# Phase 5: Prefill, Email, Classification, MCP 2.0 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire structured prefill from pasted text, an email drafter subagent, two classifiers (intent routing and injection guard), and an MCP 2.0 server that external hosts can read from but cannot write through.

**Architecture:** A `parserAgent` on Gemini with `structuredOutput` + `errorStrategy: 'fallback'` degrades parse failures to an empty form rather than a 500. `crumDecisionModel()` returns `undefined` when the key is unset so consumers state their fallback explicitly. Two `Classifier` instances share one decision model: `intentClassifier` routes user messages into schedule/task/clarify via an `intentTriageFlow` workflow, and `injectionClassifier` backs a `ClassifierProcessor` input guard that aborts with CRUM's own reason string. The `MCPServer` exposes read tools plus refuse-only write stubs, uses `requestState.key` from the existing `mcp-guard.ts`, and sits behind `createOAuthMiddleware`.

**Tech Stack:** `@mastra/core@1.79.0` (Classifier, ClassifierProcessor, Agent, MCPServer registration), `@mastra/mcp@2.5.0` (MCPServer, createOAuthMiddleware, MCP_PROTOCOL_VERSION), `@ai-sdk/typesafe-ai@3.0.24` (decision model), `ai@7.0.150`, Zod 4, Vitest 3

**Spec:** [`docs/TECHNICAL_PLAN.md`](../../TECHNICAL_PLAN.md) §6.1, §6.2, §6.5, §6.5.1–§6.5.8, §10.3, §10.3.1–§10.3.8. Phase 5 acceptance criteria from §16.

## Global Constraints

Copied verbatim from the roadmap — every task implicitly includes these:

- **Versions are pinned exactly, never with a caret.** `@mastra/core@1.79.0`, `@mastra/mcp@2.5.0`, `@ai-sdk/typesafe-ai@3.0.24`, `typescript@5.9.3`, `zod@4.6.7`, `vitest@3.2.7`.
- **A workflow step's `execute` takes one params object. A tool's `execute` takes two positional arguments.**
- **Every table carries a non-nullable `tenant_id`.**
- **Secrets are names, never values.** `TYPESAFE_AI_API_KEY` and `MCP_REQUEST_STATE_KEY` never appear behind `NEXT_PUBLIC_`.
- **`crumDecisionModel()` returns `undefined` when the key is absent** — never a half-built provider that fails on first call (§6.5.2).
- **Abort reasons are always CRUM's own string**, never provider-generated text (§6.5.6).
- **MCP writes refuse with explanation rather than suspend** (§10.3.2). The external host never sees `input_required`.
- **`legacy: 'reject'`** on the MCP server. 2025-era clients get an unsupported-protocol error (§10.3.5).

```typescript
import { createTypeSafeAi } from '@ai-sdk/typesafe-ai'

/**
 * Returns the decision model for CRUM's classifiers, or `undefined` when no
 * API key is configured.
 *
 * §6.5.2: returning `undefined` instead of a half-built provider is deliberate.
 * Every consumer then has to state what it does without one. A provider
 * constructed with a missing key does not fail at boot; it fails on the first
 * request, in production, during a customer's turn.
 *
 * Key resolution order: TYPESAFE_AI_API_KEY > JEV_API_KEY. The TypeSafe SDK
 * reads TYPESAFE_AI_API_KEY natively; JEV_API_KEY is the inherited variable
 * from the AllRounderAgent environment (§13.5) and is mapped explicitly.
 */
export function crumDecisionModel() {
  const apiKey = (process.env.TYPESAFE_AI_API_KEY ?? process.env.JEV_API_KEY ?? '').trim()
  if (apiKey === '') return undefined

  const baseURL = process.env.TYPESAFE_AI_BASE_URL?.trim() || undefined
  return createTypeSafeAi({ apiKey, ...(baseURL ? { baseURL } : {}) }).decisionModel('jev-latest')
}
```

```typescript
  name: z.string(),

  firstName: z.string(),
  lastName: z.string().optional(),
  email: z.string().email().optional(),
  phone: z.string().optional(),
  title: z.string().optional(),
  customerId: z.string().uuid().optional(),
})

export const ScheduleParseSchema = z.object({
  title: z.string(),
  startTime: z.string().datetime().optional(),
  endTime: z.string().datetime().optional(),
  location: z.string().optional(),
  attendees: z.array(z.string()).default([]),
  notes: z.string().optional(),
})

export const TaskParseSchema = z.object({
  title: z.string(),
  dueDate: z.string().datetime().optional(),
  priority: z.enum(['low', 'medium', 'high']).optional(),
  assignee: z.string().optional(),
  description: z.string().optional(),
})

/**
 * Map of object type to parse schema. Each schema is passed as
 * `structuredOutput.schema` to the parser agent. Multi-record paste uses an

export const PREFILL_SCHEMAS = {
  customer: CustomerParseSchema,
  contact: ContactParseSchema,
  schedule: ScheduleParseSchema,
  task: TaskParseSchema,

export type PrefillObjectType = keyof typeof PREFILL_SCHEMAS
```

Create `src/api/prefill.ts`:

```typescript
import { Hono } from 'hono'
import { parserAgent } from '../mastra/agents/parser'
import { PREFILL_SCHEMAS, type PrefillObjectType } from '../mastra/schemas/prefill'

/**
 * POST /api/crm/prefill/:objectType — structured prefill from pasted text.
 *
 * §6.2: uses `errorStrategy: 'fallback'` so a parse failure returns the
 * fallback value with `usedFallbackValue: true`, which the console maps to
 * an empty form with a "could not parse" notice rather than a 500.
 *
 * `jsonPromptInjection: true` is required for Gemini with tools.
 */
export function createPrefillRouter(): Hono {
  const app = new Hono()

  app.post('/:objectType', async (c) => {
    const tenantId = c.req.header('x-tenant-id')
    if (!tenantId) {
      return c.json({ error: 'x-tenant-id header required' }, 400)
    }

    const objectType = c.req.param('objectType') as string
    if (!(objectType in PREFILL_SCHEMAS)) {
      return c.json({ error: `Unknown object type: ${objectType}` }, 400)
    }

    const body = await c.req.json().catch(() => null)
    if (!body || typeof body.text !== 'string' || body.text.trim() === '') {
      return c.json({ error: 'text field required' }, 400)
    }

    const schema = PREFILL_SCHEMAS[objectType as PrefillObjectType]
    const fallbackValue = objectType === 'customer' ? { name: '', tags: [] as string[] }
      : objectType === 'contact' ? { firstName: '' }
      : objectType === 'schedule' ? { title: '', attendees: [] as string[] }
      : { title: '' }

    try {
      const result = await parserAgent.generate(body.text, {
        structuredOutput: {
          schema,
          errorStrategy: 'fallback',
          fallbackValue,
        },
        jsonPromptInjection: true,
      })

      return c.json({
        objectType,
        data: result.text,
        usedFallbackValue: result.usedFallbackValue ?? false,
      })
    } catch (err) {
      return c.json({
        objectType,
        data: fallbackValue,
        usedFallbackValue: true,
        error: 'Parse failed, please fill in manually',
      })
    }
  })

  return app
}
```

```typescript
import { ClassifierProcessor } from '@mastra/core/processors'
import { injectionClassifier } from '../classifiers/injection'

/**
 * §6.5.6 — Injection guard as a ClassifierProcessor.
 *
 * `errorStrategy: 'warn'` is fail-open: if the classifier errors, the message
 * passes through with a warning logged. This looks like the wrong side of the
 * argument until the structural controls are counted: §4.3.3's write-claim
 * guard and the §11.3 approval queue mean no injection that survives the
 * classifier can commit a write without a human. Fail-closed here would turn
 * an outage of a package marked experimental into an outage of the product.
 *
 * `lastMessageOnly: true` — only the latest user message is classified, not
 * the full conversation history.
 *
 * `maxInputLength: 8_000` — truncates before classification to bound cost.
 *
 * Abort reason is CRUM's own string, never provider-generated text (§6.5.6).
 */
export class InjectionGuardProcessor extends ClassifierProcessor {
  constructor() {
    super({
      id: 'crum-injection-guard',
      classifier: injectionClassifier,
      errorStrategy: 'warn',
      lastMessageOnly: true,
      maxInputLength: 8_000,
      onResult: (answers, { abort }) => {
        if ((answers.injection.probability ?? 1) > 0.85) {
          abort('Rejected by CRUM content policy')
        }
      },
    })
  }
}
```

```typescript
import { createWorkflow } from '@mastra/core/workflows'
import { z } from 'zod'
import { intentClassifier } from '../classifiers/intent'

/**
 * §6.5.6 — Intent triage workflow.
 *
 * Routes user messages into schedule/task/clarify paths based on the
 * intentClassifier's two questions. The workflow form is fail-closed (opposite
 * of the processor's warn): a triage workflow that cannot triage has nothing
 * useful to do.
 *
 * Three branches:
 * - schedule: intent.choice === 'schedule' && hasTimeRange.probability > 0.7
 * - task: intent.choice === 'task'
 * - clarify: everything else (including 'other' and all refusals)
 *
 * `.classifier()` does not apply fail-open behaviour. Classifier errors fail
 * the step. This is why the injection guard is a processor and the intent
 * router is a workflow step (§6.5.6).
 */
const scheduleStep = async ({ inputData }: { inputData: { message: string } }) => {
  return { action: 'schedule' as const, message: inputData.message }
}

const taskStep = async ({ inputData }: { inputData: { message: string } }) => {
  return { action: 'task' as const, message: inputData.message }
}

const clarifyStep = async ({ inputData }: { inputData: { message: string } }) => {
  return { action: 'clarify' as const, message: inputData.message }
}

export const intentTriageFlow = createWorkflow({
  id: 'crum-intent-triage',
  inputSchema: z.object({ message: z.string() }),
  outputSchema: z.object({
    action: z.enum(['schedule', 'task', 'clarify']),
    message: z.string(),
  }),
})
  .map({ message: { initData: true, path: 'message' } })
  .classifier<typeof intentClassifier.questions>('crum-intent')
  .branch([
    [
      async ({ inputData }) =>
        inputData.answers.intent.choice === 'schedule' &&
        inputData.answers.hasTimeRange.probability > 0.7,
      scheduleStep,
    ],
    [
      async ({ inputData }) => inputData.answers.intent.choice === 'task',
      taskStep,
    ],
    [async () => true, clarifyStep],
  ])
  .commit()
```

```typescript
import { MCPServer } from '@mastra/mcp'
import { listCustomersTool, getCustomerTool } from './tools/customers'
import { findContactsTool } from './tools/contacts'
import { myOpenItemsTool } from './tools/tasks'
import { knowledgeRetrieveTool } from './tools/knowledge'

/**
 * §10.3 — CRUM MCP 2.0 server.
 *
 * Exposes read tools plus refuse-only write stubs. Writes are NOT exposed:
 * an external MCP host never sees CRUM's approval gate as an approval — it
 * sees a tool that refuses with an explanation (§10.3.2).
 *
 * `requestState.key` comes from `resolveMcpRequestState()` in `mcp-guard.ts`,
 * which throws in production when `MCP_REQUEST_STATE_KEY` is unset (§13.8).
 *
 * `legacy: 'reject'` refuses 2025-era clients rather than silently
 * downgrading them (§10.3.5).
 *
 * OAuth middleware is created separately via `createCrumOAuthMiddleware()` and
 * mounted by the Mastra server at `/api/mcp/crum-crm/mcp`.
 */
export function createCrumMcpServer(requestStateKey: string): MCPServer {
  return new MCPServer({
    id: 'crum-crm',
    name: 'CRUM CRM',
    version: '0.5.0',
    description: 'Read CRM records. Writes require CRUM console approval.',
    title: 'CRUM',
    websiteUrl: 'https://crum.example.com',

    tools: {
      'crm.list_customers': listCustomersTool,
      'crm.get_customer': getCustomerTool,
      'crm.find_contacts': findContactsTool,
      'crm.my_open_items': myOpenItemsTool,
      'knowledge.retrieve': knowledgeRetrieveTool,
    },

    requestState: {
      key: requestStateKey,
      ttlSeconds: 600,
    },

    legacy: 'reject',

    mapAuthInfoToUser: ({ authInfo }) => {
      const info = authInfo as { extra?: { sub?: string; tenantId?: string } }
      if (!info.extra?.sub) return null
      return { id: info.extra.sub, tenantId: info.extra.tenantId }
    },

    cacheHints: {
      'tools/list': { ttlMs: 60_000, cacheScope: 'public' },
      'server/discover': { ttlMs: 60_000, cacheScope: 'public' },
    },
  })
}

/**
 * §10.3.4 — OAuth middleware factory.
 *
 * Returns the middleware config for the Mastra server to mount at
 * `/api/mcp/crum-crm/mcp`. Uses `createOAuthMiddleware` from `@mastra/mcp`
 * with `createIntrospectionValidator` for token validation.
 *
 * In development without `CRM_OIDC_ISSUER`, returns undefined so the server
 * can start without OAuth (the MCP guard's ephemeral key still signs
 * continuations).
 */
export function createCrumOAuthMiddleware() {
  const issuer = process.env.CRM_OIDC_ISSUER
  if (!issuer) return undefined

  // Dynamic import to avoid loading the OAuth module when not configured
  return {
    oauth: {
      resource: 'https://mcp.crum.example.com/api/mcp/crum-crm/mcp',
      authorizationServers: [issuer],
      scopesSupported: ['crm:read', 'crm:write'],
      resourceName: 'CRUM CRM',
    },
    mcpPath: '/api/mcp/crum-crm/mcp',
  }
}
```
